## Settings Tab

- File: `src/view/VicinityGraphSettingTab.ts` — extends Obsidian's `PluginSettingTab`. `display()` (line 56) calls, in order: `renderDepthDefaults()` (176), `renderSizing()` (193), `renderForceLayout()` (77), `renderExclusion()` (139), `renderPerformance()` (246). No existing visual "card" grouping beyond `.setHeading()` section titles (Obsidian's native `Setting().setName(x).setHeading()`, e.g. line 78 `"Force layout"`, line 140 `"Node exclusion"`, line 177 `"Depth defaults"`, line 194 `"Node sizing"`, line 247 `"Performance"`). These headings are flat — no fieldset/box wrapper, no accordion. For task #1 ("grouped sections"), the natural approach is either CSS-only visual framing around each `renderX()` block (wrapping container divs) or genuinely collapsible `<details>` groups per section (mirroring the in-graph disclosure pattern already used in `GraphToolbar.tsx`/`SizingSection.tsx`, see below) — no such collapsible exists in the settings tab today, only flat headings.
- Read model: settings are read straight from `PluginDataStore` (`this.store`, line 52) on each render; every control seeds from `this.store.globalDepths()`, `this.store.globalView()`, `this.store.nodeExclusion()`.
- Write model: **every** control calls `this.applyInteraction(interaction: SettingsInteraction)` (line 344), which is the exact same pure `planSettingsWrite()` contract (`src/view/settingsWritePlan.ts`) the in-graph toolbar uses. `applyInteraction` persists via `PluginDataStore` then calls `this.plugin.refreshOpenViews()` (line 364) to fan the change out to every open graph view.
- Existing sliders use Obsidian's native `Setting().addSlider()` API with `.setLimits(min,max,step).setValue(v).setDynamicTooltip().onChange(cb)` — see `addDepthSlider` (265) and `addForceLayoutSlider` (309).
- The only existing collapsible in the settings tab is a plain HTML `<details>`/`<summary>` used for "Advanced spacing" force-layout sliders (lines 103-116) — no CSS class, no styling, dependency-free (comment at line 70-76 explains why: "Obsidian's Setting API has no built-in collapsible group").
- `VicinityGraphSettingTab` constructor takes `(app: App, plugin: VicinityGraphPlugin)`; registered in `src/main.ts:63` via `this.addSettingTab(new VicinityGraphSettingTab(this.app, this))`.

## Force Layout Sliders (ticket-04, commits 3291aaf..8a0c903)

- Fully wired end-to-end through the engine's persisted `ViewSettings.forceLayout: ForceLayoutSettings` — NOT a view-only constant. Type: `src/engine/types.ts` (`ForceLayoutSettings`, fields: `centerPullStrength`, `repelStrength`, `linkStrengthFactor`, `linkGapPx`, `collidePaddingPx`, `elkNodeSpacingPx`).
- Defaults + ranges: `src/engine/constants.ts`.
  - `FORCE_LAYOUT_RANGES: Readonly<Record<keyof ForceLayoutSettings, ForceLayoutRange>>` (lines ~131-149) — single source of truth for slider min/max/step; also used by `clampForceLayoutSettings()` (persistence parser clamp) and by `GraphStructureDiff.sameForceLayout()` (compile-time-exhaustive field iteration via `Object.keys(FORCE_LAYOUT_RANGES)`).
  - `EngineDefaults.forceLayoutSettings()` — the ticket-03 shipped constants (must-not-change-default-behavior baseline).
- Settings-tab rendering: `VicinityGraphSettingTab.renderForceLayout()` (lines 77-127) — 4 "native-parity" sliders directly in the "Force layout" section (Center force / Repel force / Link force / Link distance), plus a plain `<details>` "Advanced spacing" block (Node spacing / Group member spacing), plus a "Restore force layout defaults" button (117-126) that calls `applyForceLayout(EngineDefaults.forceLayoutSettings())` then re-renders (`this.display()`).
  - Per-slider helper: `addForceLayoutSlider(container, name, desc, field)` (309-328) reads `FORCE_LAYOUT_RANGES[field]` for limits and always re-reads `this.store.globalView().forceLayout[field]` as current value; `onChange` spreads a merged `ForceLayoutSettings` object into a `global-force-layout` interaction.
- Interaction/command plumbing (`src/view/settingsWritePlan.ts`): `SettingsInteraction` kind `"global-force-layout"` (line 42, carries whole `ForceLayoutSettings` object) → `planSettingsWrite` (95-96) → `SettingsCommand` kind `"global-view"` merging `forceLayout` into `ctx.globalView`. This same interaction kind is reusable as-is by an in-graph slider component — no new plumbing needed for task #2's data path, only new UI.
- Persistence: `src/persistence/persistedShapes.ts` parses/clamps `forceLayout` via `clampForceLayoutSettings` (round-tripped through `PERSISTED_SHAPE_VERSION`).
- Live re-layout: any `global-force-layout` write → `PluginDataStore.saveGlobalView()` → `plugin.refreshOpenViews()` (Settings tab path) or `controller.handleSettingsChanged()` (in-graph path via `ControlsActions`) → `GraphViewController.runRebuild()` re-fetches the graph, then `decideLayout()` (`src/view/GraphStructureDiff.ts`) explicitly forces `"relayout"` whenever `sameForceLayout(previous, next)` is false (lines 34-36, comment explains: "a force-layout tuning change ... the sliders must re-run the layout live — reusing positions would silently swallow the new values"). `FORCE_LAYOUT_FIELDS` is derived from `Object.keys(FORCE_LAYOUT_RANGES)` so any future field is automatically compared (compile-forced).
- **Currently Settings-tab ONLY** — confirmed via `TOP_LEVEL_AGENT.md` for ticket-04 (`.ai_out/04-force-layout-sliders/main/TOP_LEVEL_AGENT.md`) and by grep: `addForceLayoutSlider`/`renderForceLayout` exist only in `VicinityGraphSettingTab.ts`; `GraphToolbar.tsx`/`SizingSection.tsx` have no force-layout UI. Task #2 is genuinely new work but the underlying settings-write path (`global-force-layout` interaction) and range table are 100% reusable — the new in-graph component should mirror `SizingSection.tsx`'s shape (a `<details className="vicinity-graph-disclosure">` reading `controls.globalView.forceLayout`, writing via `planSettingsWrite({kind:"global-force-layout",...}, ctx)`).
- Tests: `src/engine/forceLayoutSettings.test.ts`, `src/engine/settingsResolvers.test.ts` (cascade), `src/view/settingsWritePlan.test.ts` (interaction→command mapping), `src/view/d3ForceStranding.test.ts` (ticket-03 regression, must stay green at defaults), `src/view/GraphStructureDiff.test.ts` (relayout-on-force-change).

## Node Exclusion

- Type: `NodeExclusionSettings` (`src/engine/types.ts:150-153`) — `{ enabled: boolean; patterns: readonly string[] }`. Global-only (vault-wide), no per-doc override.
- Matching: `src/engine/PathExclusionMatcher.ts` — each pattern compiled as a raw case-sensitive unanchored `RegExp`; invalid patterns silently skipped; a path is excluded iff ANY pattern matches (tested against full vault-relative path incl. extension).
- Settings tab: `VicinityGraphSettingTab.renderExclusion()` (139-174) — a toggle (`addToggle`) for `enabled`, and (only when enabled) a textarea (`addTextArea`, one raw regex per line, parsed by `parseExclusionPatterns()` at top of file, lines 37-42) for `patterns`. Both route through ONE `global-node-exclusion` interaction (whole-object write, preserves the other field). Toggling re-renders (`this.display()`) so the textarea appears/disappears.
- In-graph: `src/view/NodeExclusionSection.tsx` — currently a **plain HTML checkbox** (`<input type="checkbox">`, not Obsidian's native toggle look), NOT wrapped in a `<details>` collapsible. Shows a small count badge (`excludedNodeCount`) next to the label **only when `enabled && excludedNodeCount > 0`** (line 25). It does NOT expose the pattern list in-graph — patterns are settings-tab-only by design (comment line 11: "The pattern LIST is edited in the settings tab (this pill is the quick on/off, per CLARIFICATION)").
- **`excludedNodeCount` is a COUNT ONLY — the actual excluded PATHS are not threaded to the view layer.** Trace: `VicinityTraversal.ts` — `TraversalCollector` keeps a `Set<VaultPath>` internally (`recordExcluded(path)`, ~line 204) but only exposes `excludedCount(): number` (`.size`); `TraversalResult.excludedNodeCount: number` (line 44) is the only thing that survives into `VicinityGraph.excludedNodeCount` (`engine/types.ts:252`), then `VicinityGraphBuilder.ts:69` (`ControlsModelBuilder.build(inputs, graph.excludedNodeCount)`), then `ControlsModel.excludedNodeCount` (`ControlsModel.ts:71`). **No list of excluded titles/paths reaches React.** This is directly relevant to task #3 ("when ON show what is excluded") — see Open Questions.
- Data flow for the toggle: `NodeExclusionSection` reads `ctx.nodeExclusion` (from `ControlsModel.nodeExclusion`, sourced from `GraphRequestInputs.nodeExclusion` ← `PluginDataStore.nodeExclusion()`), writes via `planSettingsWrite({kind:"global-node-exclusion", nodeExclusion:{...ctx.nodeExclusion, enabled}}, ctx)`.
- Persistence: `PluginDataStore.saveNodeExclusion()` (`src/persistence/PluginDataStore.ts:51-53`); parsed/repaired in `persistedShapes.ts` (`parseNodeExclusion`, line 214).

## Settings Propagation

- Two independent write surfaces (Settings tab, in-graph toolbar) both funnel through the SAME pure `planSettingsWrite(interaction, ctx) → SettingsCommand` contract (`src/view/settingsWritePlan.ts`) — zero duplicated merge logic. `SettingsWriteContext` = `{ globalDepths, globalView, nodeExclusion }`, always read fresh so successive edits compose.
- Settings-tab executor: `VicinityGraphSettingTab.applyInteraction()` (344-365) — switches `SettingsCommand.kind` onto `PluginDataStore` save calls, then calls `this.plugin.refreshOpenViews()` (`src/main.ts:95-100`, iterates `getLeavesOfType(VIEW_TYPE_VICINITY_GRAPH)` and calls `view.refresh()` on each).
- In-graph executor: `src/view/ControlsActions.ts` (`ControlsActionsPort` impl) — `applySettings(command)` (37-40) executes the command then calls `this.controller.handleSettingsChanged()` (`GraphViewController.ts`), which drops any pending debounce and immediately reruns the rebuild pipeline (latest-wins via monotonic `rebuildToken`).
- `GraphViewController` (`src/view/GraphViewController.ts`) is the **only** view class allowed to touch Obsidian + the async engine (architecture-map.md rule). It owns `events → engine.build → GraphStructureDiff.decideLayout → elk/d3 layout → React Flow` as a `useSyncExternalStore`-style external store (`subscribe`/`getSnapshot`). `handleSettingsChanged()` → `runRebuild()` → `decideLayout(previous, next, threshold)` decides `"relayout"` vs `"reuse-layout"`; force-layout field changes always force `"relayout"` (see above).

## Constraints / Layering

- `docs-internal/architecture-map.md` (61 lines) states the strict inward-pointing layering: `view → adapters → engine (pure core)`, with `persistence` implementing engine-defined port types. **`src/engine/` MUST NOT import `obsidian`, `obsidian-id-lib`, `react`, or `react-dom`** — enforced by `src/engine/importGuard.test.ts`. `src/shared/` is guarded by the same rule.
- `GraphViewController.ts` is explicitly the **only** view class allowed to touch Obsidian + the async engine; `VicinityGraphView.tsx` must stay a thin lifecycle shell.
- Key seams to extend via new implementations, not edits: `engine/LinkProvider.ts` (sole Obsidian→engine boundary), `view/viewPorts.ts` (`GraphSourcePort`, `GraphLayoutPort`, `NoteNavigatorPort`), `persistence/storagePorts.ts`, `adapters/obsidianPorts.ts`.
- Any UI-only state (e.g., "which disclosure is currently open") should stay purely in the DOM (`<details open>`) rather than in persisted settings or engine state — consistent with the existing pattern (toolbar/pinned/sizing disclosures carry no persisted open/closed state today).
- All styling must be theme-variable-driven — CSS files repeatedly comment "zero plugin-owned colours" / "all colours are theme vars" (e.g. `graph-view.css:391-392`, `:685`). This applies to any new Settings-tab grouping CSS too, if added.
- Force-layout ranges/defaults MUST be sourced from `FORCE_LAYOUT_RANGES`/`EngineDefaults.forceLayoutSettings()` in `src/engine/constants.ts` for both surfaces (settings tab and any new in-graph sliders) — do not hand-duplicate the numbers.

## Open Questions & Ambiguities

1. **"Show what is excluded" (task #3) has no data path today.** `excludedNodeCount` is a bare number; the actual excluded vault paths are collected as a `Set<VaultPath>` inside `VicinityTraversal`'s private `TraversalCollector` but never surfaced past `.size`. Showing "what is excluded" (a list of note names/paths) requires deciding: (a) surface the full list end-to-end (`TraversalResult` → `VicinityGraph` → `ControlsModel` → React), which is a real engine/adapter/view change (not UI-only), or (b) interpret "what is excluded" more narrowly as just showing the count/patterns-summary (already partially done via the count badge) rather than an itemized list. Needs human/product clarification on scope — this is likely the single biggest scope driver in the whole ask.
2. **Where do the new in-graph force-layout sliders' ranges/labels live?** They can trivially reuse `FORCE_LAYOUT_RANGES` + the same 6 field names/descriptions currently hardcoded as string literals in `VicinityGraphSettingTab.renderForceLayout()` (lines 78-116). Should those descriptions be extracted to a shared module (e.g. a `FORCE_LAYOUT_FIELD_META` table with name+desc) so Settings tab and in-graph controls don't duplicate copy text? Currently no such shared table exists — only `FORCE_LAYOUT_RANGES` (numbers) is shared; display strings are settings-tab-local.
3. **Native Obsidian toggle vs current checkbox for node exclusion in-graph.** The task says "make node-exclusion in graph controls a slider/toggle like in settings" — the Settings tab uses Obsidian's native `Setting().addToggle()` widget (a themed switch), while the in-graph `NodeExclusionSection.tsx` uses a raw HTML checkbox styled via `.vicinity-graph-exclusion` CSS (not Obsidian's native toggle look, since the in-graph panel is a bespoke React tree, not an Obsidian `Setting`). Does "like in settings" mean visually matching Obsidian's native toggle switch (would need a CSS-built toggle, e.g. reusing/repurposing `.vicinity-graph-sizing__toggle` checkbox style or building a new switch), or just semantically "a toggle" (which the checkbox already functionally is)? Needs clarification — likely means: restyle the checkbox to look like a switch/pill, matching the settings-tab affordance, since a native Obsidian `Setting` component can't be mounted inside the React Flow panel.
4. **Depth controls currently render unconditionally, not in a collapsible** (`CentralDepthControls` for MAIN, `GraphToolbar.tsx:40`). Task #3 explicitly says "put ALL graph-control settings under collapsibles (including depth)". This means MAIN's depth steppers — arguably the single most-used control, always visible today right below the toolbar header — must be wrapped in a further nested `<details>`. Confirm this is desired (it adds one more click to reach the most common action) vs. just wrapping the newly-added groups (force layout, exclusion) and leaving MAIN depth as the one exception, "front-and-centre" per the current code comment (`GraphToolbar.tsx:13-14`, "MAIN's depth steppers are front-and-centre").
5. **Settings tab grouping mechanism (task #1) is unspecified.** Should "visual groupings/sections" mean (a) CSS-only framed/boxed sections around the existing flat headings (no interaction change), or (b) genuinely collapsible sections (new `<details>` per `renderX()` group, consistent with in-graph patterns)? The ticket text says "so settings look more grouped" which reads more like (a), but the graph-controls half of the same ticket is explicitly about collapsibles — worth confirming these are two different mechanisms (Settings tab = static visual grouping; in-graph panel = interactive collapsibles) rather than assuming Settings tab also needs to become collapsible.
6. **No settings-tab-scoped CSS file currently exists** — verify before implementation whether Obsidian's default `PluginSettingTab`/`Setting` styling alone is sufficient for "grouped" visual sections (e.g. via `setHeading()` + spacing) or whether a new authored CSS block (in `graph-view.css` or a new file) is needed, and how it should be wired into the build (the existing `graph-view.css` is bundled specifically for the graph view's `styles.css` output — confirm the Settings tab's DOM would even be reached by that stylesheet, since `PluginSettingTab.containerEl` lives in Obsidian's global app DOM, not inside the graph `ItemView`).
7. **`ControlsModel.excludedNodeCount` reuse for a new "excluded list" feature** would likely need a new field alongside it (e.g. `excludedPaths: readonly string[]`) rather than a breaking change, to avoid rippling through every existing test fixture (`src/view/testFixtures/graphFixtures.ts:68` currently hardcodes `excludedNodeCount: 0`).
