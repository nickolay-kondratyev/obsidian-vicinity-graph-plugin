## Decision: why exactly `1.12.3`

Re-verified `npm view obsidian versions --json` (network reachable; saved to `.tmp/obsidian-versions.json`). The published 1.1x tail is:

```
1.10.0, 1.10.2-1, 1.10.2, 1.10.3, 1.11.0, 1.11.4, 1.12.0, 1.12.2, 1.12.3, 1.13.0, 1.13.1
```

Neither `1.12.4` (`manifest.json` `minAppVersion`) nor `1.12.7` (`OBSIDIAN_VERSION` in `scripts/setup-obsidian-bin.sh`) exists as a published npm typings version — the typings package does not track app releases 1:1 and jumps `1.12.3` → `1.13.0`. Exploration's conclusion confirmed.

So: **`1.12.3`, the highest published typings at-or-below the floor.** Rationale: typings must never describe APIs unavailable on the supported floor. Being slightly *below* the floor is the safe direction — it can only cause a false compile error on an API the plugin might legitimately use (loud, catchable), never a false green on an API that does not exist at runtime (silent, ships).

Pinned as the **exact** string `"1.12.3"` — no `^`, no `~` — so `npm install` cannot silently drift back over the floor. This is the whole point of the ticket; a caret range would re-admit 1.13.x.

## Root cause confirmed directly (not just inherited from the ticket)

In the newly installed 1.12.3 `node_modules/obsidian/obsidian.d.ts` line 5805, `SliderComponent.setDynamicTooltip()` carries only:

```
/**
 * @public
 * @since 0.9.7
 */
setDynamicTooltip(): this;
```

No `@deprecated` tag. In 1.13.1 the same method is tagged `@deprecated` ("The value is now always shown inline next to the slider") because the inline readout landed in 1.13.0. Reading the 1.13.1 tag as a statement about the 1.12.4 floor is what led to the call being deleted from `addLabeledSlider` in `src/view/VicinityGraphSettingTab.ts`, blanking the readout on all 10 settings-tab sliders on the supported version. The pin now makes the typings tell the truth about the floor, so that misreading is no longer reachable.

## Deliberately NOT done

- **No unit test asserting the pinned string in `package.json`.** Considered and rejected on 80/20: such a test asserts a literal against itself, restates the lockfile, and adds a maintenance tripwire on every legitimate future bump while catching nothing a reviewer of a one-line `package.json` diff would miss. The real regression it would need to catch (a `@deprecated`-driven deletion) is behavioral and already covered by the e2e slider-readout assertion in `e2e/settingsUxVisual.e2e.ts` against the pinned 1.12.7 binary. The verification here is `check` + `test` + `build` passing on the downgraded typings, plus the CLAUDE.md guardrail.
- **No `change_log` entry and no ticket closure** — TOP_LEVEL_AGENT owns both, per instructions.
- **No `main.js` / `styles.css` in the diff.** Verified they are gitignored (`.gitignore` lines 5 and 9) and untracked (`git ls-files` returns neither), so the rebuild left nothing to restore. Diff stays focused on the pin.

## Open risks

- **Three version numbers now coexist and must be reasoned about together**: `minAppVersion` 1.12.4 (manifest floor), 1.12.7 (e2e app binary), 1.12.3 (npm typings). They are intentionally not equal and *cannot* be made equal, since npm publishes no 1.12.4/1.12.7 typings. The CLAUDE.md bullet is what keeps this from being re-litigated or "fixed" by a future bump to `latest`.
- **Typings sit 1 patch below the floor**, so an API introduced in app 1.12.4 would not type-check. Nothing in the current source needs one (`npm run check` is green), and this failure mode is loud rather than silent — acceptable, and the safe direction.
- **Future bumps need a deliberate choice**: when `minAppVersion` rises, the pin should move to the highest published typings at-or-below the new floor, not to `latest`.
- `npm run test:e2e` (real-Obsidian release gate) was **not** run — it is not part of `npm test` and needs the downloaded binary. This change touches only compile-time typings and cannot alter runtime bundle contents (`obsidian` is `external` in `esbuild.config.mjs`, never bundled), so e2e behavior is unchanged by construction. Worth running at the normal release gate regardless.
