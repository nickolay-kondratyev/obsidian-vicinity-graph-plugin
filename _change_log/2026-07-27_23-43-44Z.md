## Problem

Every settings-tab control wrote through an unserialized async handler. Two clicks on the same control inside one save round-trip started two independent handlers, and whichever FINISHED last won the store — not necessarily the last one CLICKED. The checkbox in the DOM showed the last click, so the store and the visible control could disagree until the tab was re-displayed.

Pre-existing and tab-wide. It was previously masked on the exclusion toggle because that handler ended in a full `display()` that re-seeded the checkbox from the store; removing that repaint (nid_9k11zke41l6ze3p7n7suuo4v2_e) unmasked it.

## Fix

New pure `src/view/settingsWriteQueue.ts` — a single pre-caught promise tail using the idiom already established by `PluginDataStore.writeChain` and `DebouncedSettingsWrites.draining`, so one rejected write cannot wedge the chain while the failure still reaches its own caller. `VicinityGraphSettingTab` holds one queue and enqueues all 8 interaction write paths.

**The non-obvious part**: queueing `persist()` alone would NOT have fixed this. Both toggle handlers read their store snapshot AFTER `await settlePendingWrites()`, so two handlers could resume off the same stale snapshot regardless of write ordering. The serialized region therefore starts BEFORE the snapshot read — `settle -> snapshot -> plan -> persist -> refresh` is now atomic per interaction and runs in click order. The force-layout slider read moved inside the task for the same reason.

Debounced thunks stay off the queue by design: a queued task drains them via `settlePendingWrites()`, so enqueuing there would deadlock. They are already ordered by `drain()`, and their read-to-persist is one synchronous stretch.

Rejected alternative: re-seeding each control from the store after its own write — that reintroduces the focus-stealing repaint this ticket family exists to remove.

## Testing

Colocated BDD test on the pure queue with an injected gate that forces the earlier task to finish LAST — the ticket warned that a naive double-click test passes with or without the fix, since identically shaped await chains resolve FIFO in practice. Falsification was verified twice independently (implementer and reviewer) by stubbing `enqueue` to a pass-through: 2 failed | 2 passed, then restored to green. Ordering, rejection isolation, and caller-visible failures are all covered.

The tab itself has no vitest harness (node env, no jsdom, `obsidian` is types-only), so the pure-module unit test follows existing repo precedent rather than adding e2e.

`npm test`: 83 files / 1143 tests pass. `npm run check`: clean.
