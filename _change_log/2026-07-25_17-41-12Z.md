Closes ticket `nid_5wiribg2mn0mqcr7ni4ya0cfe_e`. Sliders rendered via Obsidian
`Setting.addSlider(...)` produced a bare `input[type=range]` with no programmatic
association to the visible name, so a screen reader announced all seven force-layout
sliders identically.

## What changed
- `src/view/VicinityGraphSettingTab.ts`: one rule (`nameControl`) applied through one
  shared row builder (`addLabeledSlider`, now used by all 10 sliders including the
  formerly inline "Outline depth") plus the number/textarea helpers. Adding an 8th row
  inherits the accessible name with no extra work.
- `e2e/settingsUxVisual.e2e.ts`: real-DOM guard asserting no `input`/`select`/`textarea`
  under `.vicinity-graph-settings` lacks an accessible name, with a positive floor so
  "matched nothing" can never read as "all good". Radio/checkbox exemptions are explicit
  and ticket-linked.
- `src/view/ForceLayoutSection.tsx` already set `aria-label={meta.label}` — that part of
  the ticket was stale; left untouched.

## WHY-NOT a vitest DOM test
Vitest runs in a `node` environment and `node_modules/obsidian` is types-only
(`"main": ""`), so a real `Setting` cannot be constructed. Asserting a hand-written
`Setting` fake would test the fake, not Obsidian — the guard lives in e2e instead.

## Near-miss worth remembering
An intermediate commit removed `setDynamicTooltip()` because the typings mark it
`@deprecated` ("value is now always shown inline"). That tag ships with obsidian@1.13.1
typings, but `minAppVersion` is 1.12.4 and e2e pins 1.12.7, where the method still
installs the hover listeners that are a slider's ONLY value readout. The full suite
stayed green while every tab slider silently lost its value; a DOM probe on 1.12.7
caught it and the call was restored with a WHY comment. Follow-ups filed:
`nid_14phm98g7w64oparxz5wvfqwh_e` (assert slider value visibility),
`nid_6kms4zn8o8c8r7g983oqlvvky_e` (pin the `obsidian` devDep to the supported floor).
