Step 2 of the settings-cleanup chain (`docs-internal/notes/settings.md`), ticket `nid_wimjq4ewgbg21n4zx9d4qq3a0_e`.

## Problem

Adding one settings field cost ~180 lines across ~15 files and touched ~8 hand-maintained parallel lists that failed **silently** when one was missed. That drift had already produced multiple symptom tickets.

## What changed

Five previously-silent sites now fail COMPILATION and **name the offending field**:

1. `parseViewOverride` branch table (`src/persistence/persistedShapes.ts`) — a new field could previously be dropped forever on load
2. section reset map (`src/view/settingsSectionFields.ts`, new) — a field could belong to no section reset
3. `SIZING_METRICS` (`src/view/sizingMetrics.ts`) — was an unguarded order-bearing array
4. spec entries (`src/engine/SettingsSpec.ts`) — both missing entry and orphan entry
5. `SizingRangeField` — was a hand-typed union, now derived

A sixth (depth parse) was found and guarded during review. Deriving `SettingsResetScope` additionally means a new settings *section* now compile-forces a reset spec — previously unguarded entirely.

The `absent override = inherit` rule (`!== undefined` presence semantics) went from 7 hand-written sites to **one** `definedFieldsOnly` helper.

Live defect fixed: the in-graph panel force-layout "Restore defaults" button built its own defaults via `EngineDefaults.forceLayoutSettings()` — a fourth independent copy — and now routes through the shared reset plan.

## Verification

`npm test` 1144 passed (baseline 1131) + 1 pre-existing expected fail; `npm run check` exit 0. All test changes are **+219/-0** — pure additions. `src/view/settingsResetPlan.test.ts` is byte-identical to its pre-branch state, which IS the refactor's correctness proof.

The review re-ran every compile-guard probe independently, proved the inherit invariant at runtime (pinned `0`/`false` survive; absent fields stay absent *keys* — significant because `exactOptionalPropertyTypes` is off), transcribed the six pre-branch reset closures to confirm the derived plans emit identical commands, and injected a defect to confirm the guards catch it.

## Acceptance amended by the owner

The ticket's literal *"adding a new field requires editing ONE declaration"* was **not** met — five edit sites remain, four compiler-named. The only route there would derive `ViewSettings` from a runtime array, weakening `ViewSettingsResolver.resolve()`'s return-type completeness, which standing constraints forbid. The owner ratified **"compile-forced N declarations"** as the bar: the failure mode this chain kills is *silent* drift, and compile-forced is not silent.

## Scope held

No renderer-loop rewrite (ticket 4), no depth rename (ticket 6), no user-facing copy change, no CSS class rename, no persisted-shape change, zero e2e churn.
