Closes ticket `nid_s676x55uojmtcwh9t4l9mc6zl_e`.

## Problem

The plugin re-detected, on EVERY graph rebuild, where canvas outgoing links come from. Detection
read `metadataCache.resolvedLinks`, which fills asynchronously at vault boot, so a session landed on
either `core-indexed` (canvas links from Obsidian core, INCLUDING wikilinks inside canvas TEXT
nodes) or `fallback-required` (our `CanvasFallbackParser`, file-type nodes only). The two regimes
produced different edge sets, so the same vault rendered a different graph depending on boot timing
— measured 10 vs 11 edges across repeated e2e runs.

## Decision (human)

A wikilink written inside a canvas TEXT node DOES produce a graph edge. Fixed by unifying the two
regimes rather than by caching the detection result, so the race becomes benign by construction.

## Change

- `CanvasFallbackParser` harvests wikilinks (`[[x]]`, `![[x]]`) from canvas text-node bodies via the
  new `src/shared/Wikilinks.ts`; resolution reuses `MetadataCachePort.getFirstLinkpathDest`, the same
  path markdown links take. No port change needed.
- The regime is now decided PER CANVAS instead of per install: `detect(keys)` became
  `detectFor(resolvedLinks, canvasPath)`, an exact key lookup. Review caught that a vault-wide
  verdict had a worse instance of the same bug — a vault with one indexed and one unindexed canvas
  lost ALL edges for the unindexed one. The `canvasCapability` field is gone; regime state IS
  `canvasOutgoingByPath` membership, so the consuming methods lost branches rather than gained them.
- Text-node scanning sits inside the mtime-keyed `CanvasParseCache`, so per-build cost is unchanged.
- `ensureCanvasFixtureIsIndexed()` deleted from the e2e eval harness (vestigial once the regime is
  pinned); a second dev-vault canvas guards the partial-index case.
- Plan doc records the settled semantics and drops the `Deferred to V2+` entry.

## Verification

5x `npm run test:e2e -- edgeRoutingEval.e2e.ts` → 11 edges every run (was a 10/11 coin flip). Four
instrumented probe runs landed on BOTH regimes and still produced 11. `npm test` 1082 passed,
`npm run check` clean.

## Known residual

Markdown-style `[a](b.md)` links in text nodes and `[[links]]` inside code spans still differ
between regimes — deferred to `nid_ygo7h95ssgmunaqsprc1zlmfh_e`, documented in code and plan doc.
Edge ORDER also differs between regimes, but order does not feed truncation or top-N selection
(verified: `NodePriorityChain` ends in a total lexicographic order, `GraphStructureDiff` compares
Sets), so it is not user-visible.
