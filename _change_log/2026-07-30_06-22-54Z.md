Ticket nid_itpt4tf0kkhsbbz0np304a558_e.

Before: several settings write promises were fire-and-forget (`void`) — the debounce drain, the settings tab's `apply`, the in-graph `restoreDefaults` — so a rejected persist was silent.

Now: `SettingsWritePipeline.write()` catches, logs the cause, and raises ONE notice naming the setting's DECLARED label (from `settingsRows.ts` / `SETTINGS_RESET_SCOPES`, nothing hand-typed). The refresh fan-out still runs so views repaint what IS stored. Call sites keep their `void` and gained no try/catch.

- Notice surface behind `UserNoticePort` (`src/view/viewPorts.ts`), implemented over `Notice` in `src/main.ts` only, faked by `src/view/FakeUserNotices.ts` — same shape as `ViewsRefreshPort`.
- Copy in the new pure `src/view/settingsWriteFailureNotice.ts`; a walk over every declared row pins that a control *kind* can never leak into user copy.
- POLS note now documented in code and `docs-internal/architecture-map.md`: a resolved write promise means 'attempted and reported', not 'stored'. And `PluginDataStore.persist()` assigns in-memory state before `saveData`, so after a failure the session keeps the unsaved value — there is no snap-back, the notice is the only signal.
