Ticket nid_o5a1055jyynn9nohpb5rj2vqp_e.

`ControlsActions.pinNode`/`unpinNode` ran on the settings chain but OUTSIDE its catch, so a rejected `data.json` write rejected the promise the React handler `void`s (unhandled rejection), showed the user nothing, and left the pin in memory rendering as pinned until a restart.

- `src/view/settingsWritePipeline.ts`: the pipeline's single `try` became a private `guarded()` that owns BOTH the catch and the fan-out, keyed on a `GuardedWriteOutcome` (`store-changed` | `store-unchanged`) the body returns. New public seam `runGuarded(subject, task)` covers a non-settings serialised write, so there is still ONE catch and ONE fan-out — production code now has exactly one `refreshAllViews()` call, down from two.
- A REFUSED pin (no stable id — nothing moved) rebuilds nothing; a REJECTED persist repaints, because `PluginDataStore.persist()` moves `this.data` before `saveData`, so skipping the repaint left the screen holding the stale copy.
- Copy stays in `src/view/settingsWriteFailureNotice.ts` behind a closed `NonSettingsWriteSubject` union — no call site types user-visible text. `ControlsActions` no longer holds its own `ViewsRefreshPort`.
- Test double `src/persistence/RejectingPluginDataPort.ts` lifted out of the pipeline suite and reused.

Tests: 1290 → 1294 passing, none removed; `npm run check` clean. In-memory rollback on a failed write remains out of scope (open ticket nid_biwdtykvazsk3ejcqqli8o9j7_e).
