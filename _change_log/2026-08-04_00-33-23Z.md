Three defects found reviewing 36354cd (docid-keyed per-node overrides):

1. `src/main.ts` `handleVaultDelete` pruned only the pinned set, so a deleted doc's `nodeOverrides` entry survived until the next startup sweep. Both maps now drop through ONE `PluginDataStore.forgetDocs(docids)` — also used by `OrphanSweeper` (one data.json write instead of two), so a third docid-keyed map is wired in a single place. `hasPin` was the guard that call replaced and is gone.
2. `PluginDataStore.saveNodeOverride(docid, completeOverride)` was wholesale-replace: a consumer had to compose the entry from `GraphNode.override` (the rendered snapshot) and would clobber the field another view stored since that rebuild — the exact failure the settings pipeline forbids. Replaced by field-scoped `NodeOverrideChange` + `saveNodeOverrideField` / `clearNodeOverrideField`, which merge over state read fresh in the store. A compile-time assert keeps every `NodeOverride` field writable.
3. `PersistenceServices.saveNodeOverride(file, {})` reached `ensureDocId`, minting frontmatter into a note to store nothing. Clearing now goes through read-only `getDocId` (an id-less doc owns no override) and reports no verdict, like `unpinDoc`.

Also: the sweep completion log reports `overridesRemoved`. Cold-docid-map window (pins AND overrides invisible until the 15s sweep) filed as nid_gbyqsuplz8b7pv0u5k34sdz1q_e.

Verified: npm run check clean, npm test 1507 passed, npm run test:e2e vicinityGraph.e2e.ts 25 passed.
