CLARIFICATION requirement 3 of `node-content-preference` says `sizePx` MUST NOT depend on
`ViewSettings.nodePreviewPreference` — otherwise every preview-pill flip crosses
`SIZE_RELAYOUT_THRESHOLD` and forces a full relayout instead of a data-only refresh.
Nothing asserted it. The pre-existing guard in `GraphStructureDiff.test.ts` only pins that
nobody adds a preference trigger to `decideLayout`; it hands `decideLayout` fixed sizes, so a
coupling introduced inside the sizer would slip past it.

Three guards added, at the altitudes where the coupling could actually be introduced:

- `src/engine/NodeSizer.test.ts` — sizes one fixture under every `NODE_PREVIEW_PREFERENCES`
  value, asserting identical `sizeScore`/`sizePx`. Non-tautological: the settings object handed
  to `computeSizes` carries the preference (plain structural typing, no production signature
  widened), so a sizer that starts reading it goes red.
- `src/engine/VicinityEngine.test.ts` — same invariant across the real
  `ViewSettingsResolver -> NodeSizer` seam, which is where routing `viewSettings` wholesale into
  a new size metric would surface.
- `src/view/flowMapping.test.ts` — flow-node geometry constant across preferences.
  `vicinityGraphToFlow` has the preference in scope and sets width/height, so "image previews
  need a taller box" is the most plausible way this invariant dies.

Each was mutation-verified: a deliberate size<->preference coupling at that layer was shown to
fail exactly the corresponding new test, then reverted. Declined a `nodeDimensionsPx` guard in
`graphIdentity.test.ts` — it takes a `GraphNode` with no settings, so the test would assert
`f(x) === f(x)`. The pointer comment in `GraphStructureDiff.test.ts` now names the three guards
instead of saying the invariant still needs pinning.

No production code changed. Suite 1014 tests green, `npm run check` clean.
