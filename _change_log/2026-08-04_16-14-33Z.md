Review of 868a5b9..HEAD, second round (the first round is 2026-08-04_15-55-53Z). Fixed:

1. **Resize grips were clipped by the node's own `overflow: hidden`.** `.vicinity-graph-node` must clip its title/thumbnail, and React Flow centres every `NodeResizeControl` ON the node's edge — so nesting the grips there cut each one down to the sliver falling inside the padding box: the 1px edge lines rendered as a half-pixel, and only the inner quadrant of the 9px corner chip survived. Verified live with `document.elementFromPoint`: at the old nesting a point in the grip's outer half returned `react-flow__pane`. `NoteNode` now returns a fragment — the three grips are SIBLINGS of `.vicinity-graph-node`, children of the React Flow node wrapper, which is positioned and clips nothing — and the CSS is rescoped to `.vicinity-graph-flow`. This also falsifies the shipped WHY-NOT note that claimed the handle "overhangs the node box" (it did not); the opacity-only reveal and its bistability reasoning stand.

2. **A press on a grip that never MOVED focused the note.** d3-drag suppresses the follow-up click only once the pointer has moved, so a mis-grabbed handle bubbled a plain click to the RF node wrapper and `onNodeClick` made the note MAIN. `startedOnResizeGrip` (src/view/nodeResize.ts) guards it. Verified failing before the fix.

3. **`VicinityGraphFlow` gated its render-phase reseed on a `useMemo` identity.** React may drop a memo cache at will, and a recomputed mapping would have read as a fresh publish and discarded the box a drag is holding. The gate is now `snapshot.nodes` — the published array itself.

4. Corrupt YAML in `_tickets/view-drag-to-resize-...md` (`links: [[a, b]` + a stray continuation line — written by `ticket link`, which still reproduces it).

Filed nid_sj9qg27cmear9lgdlz5umwra5_e: a resize UNDER `SIZE_RELAYOUT_THRESHOLD` reuses both the layout and the cached folder-group box dimensions, so a node dragged ~1.5x can overlap its neighbours until an unrelated structural change. Product call, left unpatched.
