Implements ticket nid_var2o7krxq7ribq3iofni3aw1_e via the React Flow floating-edge pattern: `VicinityEdge` looks up both endpoint nodes with `useInternalNode`, builds absolute `ClipRect`s, and `facingSideAnchorsFor` (new, pure, in `edgeGeometry.ts`) intersects the centre-to-centre segment with each border. Built on the existing Liang-Barsky `segmentRectEntryPoint` -- no second intersection routine. `edgePathFor` is byte-unchanged; handles, layout and the routed branch are untouched.

## Reach is narrower than the ticket implied

The ticket justified this with the `edgeRouting` OFF setting and `radial` layout. **Both were deleted** by tickets closed 2026-07-24, so neither exists. The degenerate `clipRouteToEndpointRects` chord -- the remaining normal-operation case -- emits a 2-point route and therefore takes the ROUTED branch, never reaching the new anchors; that degeneration was proven mutually exclusive with having usable facing anchors. **So this is a no-op in normal operation**, active only on router/wasm failure, absent-route, and dropped-edge paths. `docs-internal/specs/graph/arrows.md` states this plainly. Follow-up `[decide]` ticket nid_bq5k5gx5k3112otsbz1u0h7ba_e covers the multi-vertex remainder (~0.5%, corner-overlap).

## Review caught a real bug

Partially overlapping boxes produced a REVERSED segment (arrowhead pointing at the wrong node). Fixed with a dot-product ordering guard; degenerate, touching, and non-finite rects fall back to the handle endpoints rather than emitting NaN.
