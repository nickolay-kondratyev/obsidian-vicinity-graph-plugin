Adding a settings field touches 6 production files; 5 of those steps were already compile-forced or loudly tested. The last silent one was declaring the ROW in `SETTINGS_GROUPS` (`src/view/settingsRows.ts`) — a leaf that was specced, parsed, persisted and reset but never given a row COMPILED, ROUND-TRIPPED and SHIPPED as a setting no user could reach except by hand-editing `data.json`. `settingsRowParity.test.ts` walks the ROWS, so a missing row was just a smaller walk that still passed.

`src/view/settingsRowSpecCoverage.test.ts` (new, tests only — no production change) closes it with 4 BDD tests:
- every declared settings field is edited by some row in `SETTINGS_GROUPS`; the failure names the leaf and tells the maintainer how to fix it
- no stale mapping: every id the mapping produces still exists as a declared leaf, so the dotted paths cannot rot and the coverage test cannot pass by matching nothing
- the field walk is non-vacuous
- no two rows edit the same field

The row -> leaf join is `specLeafIdFor(control)`, a switch closed by `unhandledRowControl` — a new control kind is a compile error, and a new field in an existing family needs no edit here. Deliberately shipped WITHOUT an allowlist const: no leaf is intentionally row-less today, so the escape hatch lives in the failure text (add the row, or add an id-keyed allowlist with a reason plus its anti-rot tests, modelled on `BOUNDS_ENFORCED_OUTSIDE_THE_ENGINE`).

Verified by actually making it fail: removing the "Embeds out" row makes this suite — and only this suite in the whole repo — fail naming `globalDepths.embedDepthOut`. `npm test` (92 files / 1217 tests) and `npm run check` green with the row present.
