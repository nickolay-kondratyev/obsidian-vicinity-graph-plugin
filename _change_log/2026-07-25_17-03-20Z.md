Ticket nid_u36pqr4zljs44jt42lk9ln8ry_e.

**Bug**: `ControlsActions.applySettings` persisted then called only `controller.handleSettingsChanged()`, so only the owning view rebuilt. With two graph views open, a global setting change left the other view stale — visibly, since the node-content-preference radio is controlled off the snapshot (second view showed the wrong segment selected).

**Fix**: new `ViewsRefreshPort { refreshAllViews() }` (`src/view/viewPorts.ts`), implemented in `src/main.ts` over the existing `refreshOpenViews()` and threaded registerView -> VicinityGraphView -> ControlsActions. Scope decision lives in the pure, exhaustive (compile-time-checked) `src/view/settingsWriteScope.ts`; `FakeViewsRefresh` records refreshed views for tests. Global commands AND pin/unpin fan out; per-doc depth writes stay on the owning view. The originating view is not rebuilt separately — the fan-out already enumerates it (verified).

**Also**: `WriteOutcome` makes it uniform that nothing landed => nothing rebuilds (rejected pin, null MAIN, non-persistable per-doc), replacing unconditional refreshes. Two ctor narrowings for testability: `OwningViewPort` instead of `GraphViewController`, `VaultPort` instead of `App`.

**Tests**: first-ever `ControlsActions.test.ts` (11 tests) + `settingsWriteScope.test.ts`. Started red; suite now 938/938, `npm run check` clean.

**Follow-up filed**: `docs-internal/tickets/ticket-per-doc-write-leaves-sibling-views-stale.md` — review found the per-doc narrowness is a deliberate scope boundary, NOT an invariant: sibling views follow the active file and share MAIN, so they do go stale on a depth write. Out of scope per this ticket's acceptance criteria.
