`src/engine/SettingsSpec.test.ts` had two tests promising the defaults/limits equal "the exact shipped baseline", but both hand-listed the top-level `ViewSpec` fields — and both omitted `outlineMaxDepth`. The field was never asserted there, and the shape made under-population invisible: adding a key to `SETTINGS_SPEC.globalView` went unnoticed.

## What changed

- `outlineMaxDepth` pinned on both sides of BOTH baselines (default `2`; limits `{min:1,max:6,step:1}`).
- Compile-time exhaustiveness, reusing the repo idiom from `src/engine/types.ts`:
  - `EverySpecField<TSpec> = Record<keyof TSpec, unknown>` for the defaults baseline;
  - `SpecLimitsBaseline<TSpec>` for the limits baseline, which derives each field's required bound keys (`min`/`max`/`step`) from the spec itself.
  Applied via `satisfies` to the `ViewSpec` / `DepthSpec` / `NodeExclusionSpec` / `SizingSpec` literals.
- Net effect: a new spec key, a removed key, a bounded field dropping a pin, or a default-only field GAINING bounds is now a `npm run check` error that names the offending key.
- `depthStepper` restated as a guarded `globalDepths` entry — strictly additive (old `min:0`/`max:5` kept, `step` + `incomingDepth` added).

## Why it took two rounds

The first pass introduced a `NO_SPEC_LIMITS` marker that sat on both sides of the `toEqual` — a constant compared with itself, asserting nothing. Review caught it with a probe (a default-only field gaining limits stayed green). The reviewer's suggested replacement type would itself have forced deleting the `max`/`step` pins the ticket had just added, because `satisfies` does excess-property checking; the implementer diverged to a form that derives bounds per field instead. Reviewer confirmed that call on re-review.

Every guard was proven RED-before-GREEN with a temporary spec probe, independently by both implementer and reviewer.

## Known limitation (accepted)

`SpecLimitsBaseline` inspects only a field's DIRECT bound keys, so composite sections (`sizing`, `nodeExclusion`) map to `{}` — nested bound drift inside them is still invisible. Closing only `nodeExclusion` would have been false symmetry, so both were left.

## Scope

Tests only — `src/engine/SettingsSpec.test.ts` (+79/-15), no production code touched. `npm test` 922 passed / 0 failed; `npm run check` clean.

The `linkStrengthFactor.max` baseline was left untouched per the ticket. Note it is NOT currently RED — `main` re-pinned it to `4` in `258ec5a`; `docs-internal/tickets/ticket-settings-baseline-tests-stale-after-spacing-change.md` annotated accordingly and left open for a human.
