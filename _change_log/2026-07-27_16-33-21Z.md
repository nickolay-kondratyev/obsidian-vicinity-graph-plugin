`ObsidianHarness.prepareVaultCopy` (`e2e/obsidianHarness.ts`) already deleted `.obsidian/plugins/vicinity-graph/data.json` from the throwaway vault copy so stale GLOBAL settings could not leak into a launch — but it left `doc-data/`, where PINS live. A pin created by a human during manual QA in `.dev-vault` was therefore copied into every subsequent e2e vault copy, which would spuriously fail the "WHEN no central is pinned THEN the panel has no Pinned centrals disclosure" assertion in `e2e/settingsUxVisual.e2e.ts`. Loud, never a silent false green.

- `prepareVaultCopy` now also `rmSync`s the `doc-data/` dir (recursive), destination literally rooted at `VAULT_COPY_DIR` so the `e2e/vaultTarget.test.ts` destructive-call scan stays un-weakened. WHY comments extended; `ObsidianHarness` class doc updated.
- New `e2e/vaultCopyReseed.test.ts` cross-checks the `doc-data` literal in `src/main.ts`'s `docDataDirPath()` against the harness wipe, so a future rename cannot silently break the reseed. Read-only `fs` members only. Verified to fail on drift in both directions.
- Verification: `npm test` 1011 pass, `npm run check` pass, `npm run test:e2e -- settingsUxVisual.e2e.ts` 17/17 green against real Obsidian 1.12.7. Honest gap: `.dev-vault`'s `doc-data/` was empty at the time, so that e2e run proves no regression rather than proving the repair; the repair itself was proven with a scratch-copy negative control (planted pin survives without the fix, gone with it).
- Follow-ups filed, not fixed here: `nid_7fq9y51mbucmduzf9z31hmwmq_e` (the `"doc-data"` literal is duplicated across 5 sites — a shared constant should replace it, and should delete the new drift guard), `nid_0jzq3ev878kjd0zhn3zxyje8q_e` (`.obsidian/workspace.json` leaks human-QA state into the copy the same way).
