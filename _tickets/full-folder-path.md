IN the grouping settings when we have full folder path to show in the folder, we should use elipses on the front of the path and not the back.

Right now we use elipses at the back that eats the most important part of the path.


So instead of the 
```
ancestor-path/some/chil...
```

We should have something like
```
...ath/some/child-path
```

When we need to use elipses.

And better yet divide it by `/` instead of 

```
ancestor-path/some/chil...
```
Show
```
.../some/child-path
```

WHen the elipses need to be used so that we don't cut words halfway and just use `/` as delimiter and cut paths cleanly.

## Resolution

**What was changed:** the folder-group label (`.vicinity-graph-group__label`) now
truncates from the FRONT instead of the back, so an over-long "Full folder path"
label eats its ancestor head (`…/some/child-path`) and keeps the meaningful leaf
tail visible.

**Where:** `src/view/graph-view.css` — added `direction: rtl; text-align: left;`
to the existing `overflow: hidden; text-overflow: ellipsis` rule (`styles.css`
regenerated by `npm run build`, a build artifact). No TS/TSX change was needed:
`FolderGroupNode.tsx` keeps rendering the FULL path text in the DOM and the label
truncation was already purely visual (CSS).

**Why CSS-only (invariant that shaped the approach):** the full folder path must
stay in the DOM — it is the group's `title` tooltip and the
`nestedGrouping.e2e.ts` label tests assert `toHaveText(fullPath)`. `direction:
rtl` flips only the VISUAL ellipsis side while leaving the DOM text and glyph
order (latin paths) intact. `text-align: left` keeps a label that fits
left-aligned exactly as before.

**Deliberate non-goal — the "better yet" clean `/`-boundary cut
(`.../some/child-path`).** Not implemented. A pure-CSS ellipsis can only cut at
the CHARACTER boundary, so cutting cleanly at `/` would require JS width
measurement AND replacing the rendered DOM text with a shortened string — which
breaks the full-text-in-DOM invariant (tooltip + width-independent e2e text
assertions) and makes the label width-dependent/flaky. Low ROI versus the
front-ellipsis fix, which already resolves the core complaint (the ellipsis no
longer eats the most important, trailing, part of the path). Left as a possible
future refinement if a measured/segment-aware label is ever wanted.

**Verification:** `npm run build` (green) + `npm run test:e2e -- nestedGrouping.e2e.ts`
(7/7 passing — full-path label text and tooltip still assert correctly).
