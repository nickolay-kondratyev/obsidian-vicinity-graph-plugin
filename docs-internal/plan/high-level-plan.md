# Local Graph Plugin: High-Level Plan

An Obsidian plugin that replaces the local graph view with a React Flow based view. It exists to fix the two core weaknesses of the native graph: every node looks the same, and there is no grouping. Nodes become rich, informative components grouped by folder, sized to fit the content they show, traversed with per-channel depth control.

## Goals

1. **Nodes that carry information.** Title, first image thumbnail, attachment icons, folder identity, visual emphasis by relevance. A node should tell you what the note is before you open it.
2. **Grouping by folder — RECURSIVELY.** Folder membership is visible structure in the graph, not invisible metadata: nested folders render as nested boxes to arbitrary depth, and a note falls into its nearest qualifying ancestor folder so its whole containing chain is part of the picture. See **Folder grouping (recursive)** under Decisions for the signed-off rules.
3. **Per-channel depth control.** Plain outgoing links, embedded outgoing notes and incoming links each have their OWN depth budget ("Links out" / "Embeds out" / "Links in"), adjustable from the view rather than buried in a settings tab. The budgets are GLOBAL per ROLE (owner decision 2026-07-29, ticket `nid_ez38gf1mrdgh5kxedzrdicwzl_e`): one trio for the active note, a second trio for pinned centrals ("Pinned links out" / "Pinned embeds out" / "Pinned links in", ticket `nid_ts4rx2pfo6o18verzk07z16g8_e`) — there is no per-document memory.
4. **Pinned central nodes.** Hold one or more vicinities on screen while browsing elsewhere.
5. **Focused, bounded views.** Hard node cap with deterministic truncation. Above ~100 nodes a graph stops being interesting; we optimize for the readable range instead of chasing scale.
6. **Feels native.** Obsidian theme variables, sidebar placement, canvas support.

## Scope: V1

- **LOCAL graph only.** No global graph.
- No unresolved (ghost) links.
- Sizing CONFIGURATION is global only. The one per-note size is the user's own: a drag-to-resize commits a docid-keyed `sizePx` override (see Rendering and interaction) that wins over every dial. Per-VIEW sizing overrides come later once the data format settles.
- No manual node dragging persistence; layout is computed.

## Terminology

- **MAIN**: the node whose editor is currently active.
- **Central nodes**: MAIN plus every pinned node. Centrals are traversal roots.

## Decisions

### Stack

- **React Flow** for rendering. Chosen because custom nodes are React components (rich node content is the core requirement) and subflows provide native grouping. Accepted tradeoff: no built-in layout, DOM-based rendering caps practical size at a few hundred nodes, which the node cap makes irrelevant.
- **elkjs** for layout. It is the layout engine that understands hierarchical containment, so folder groups lay out correctly. Dagre does not handle compound layout; do not spend time on it.
- **TypeScript + esbuild** standard plugin toolchain, **React 18** mounted in an ItemView, **vitest** for the pure layers.
- **docid library** lives as a git submodule at `submodules/obsidian-id-lib`. Its README is the source of truth for id creation and usage.
- `minAppVersion` set to the Obsidian version that introduced canvas `metadata.frontmatter`, which the id scheme depends on.

### Graph model and traversal

- Traverse on demand at graph build time via the Obsidian API. **No persistent link cache of our own**, so no cache invalidation. Obsidian maintains the indexes.
- Outgoing links from `resolvedLinks`; incoming links via `getBacklinksForFile` per visited node. Per-node lookup scales with nodes visited (bounded by the cap), not vault size, and delegates index maintenance to Obsidian.
- **Multi-root per-channel BFS**: independent BFS per central node × per CHANNEL, results unioned and deduped. A channel is one relationship the walk follows, with its own budget — a flat enum, not a direction × kind matrix, because the incoming side is kind-blind by scope:

    | Channel | Follows | Budget (`DepthSettings`) | UI label |
    |---|---|---|---|
    | `outgoing-link` | plain `[[x]]` / `[x](y)` references | `linkDepthOut` | Links out |
    | `outgoing-embed` | embedded NOTES (`![[x]]`, canvas file nodes) | `embedDepthOut` | Embeds out |
    | `incoming` | every linker, kind-blind | `linkDepthIn` | Links in |
    | `descendants` | folder-note CHILDREN (`getChildNotes`), parent → child | `descendantDepth` | Descendants |
    | `ancestors` | folder-note PARENT per hop (`getParentNote`), parent → child | `ancestorDepth` | Ancestors |

    `CHANNEL_DEPTH_FIELD` (`engine/types.ts`) is the single mapping; `Record<Channel, …>` makes a new channel a compile error until it is given a budget. The last two are the **folder-note hierarchy** channels (plan `nid_ri1d36t7hmhu0kr652wny1dmz_e`, see **Folder-note hierarchy** below); they carry a `hierarchy` `ChannelRelation` rather than `link`, so they are invisible to `getLinkCount` and the cross-links sweep, and both emit their edge parent → child regardless of walk direction.
- **The channels are KIND-PURE** (owner decision D1, ticket `nid_fay1hu5sxcoygizopkkg0f0d7_e`): each runs its own BFS and the results are unioned, exactly as outgoing/incoming already did. The accepted cost is that a chain which CHANGES KIND mid-way (`a ![[b]]`, then `b [[c]]`) is walkable by neither channel, so `c` does not appear. This is invisible at the shipped ONE-HOP defaults (`embedDepthOut === linkDepthOut === 1`, where the two outgoing channels union to exactly the old kind-blind outgoing walk) and appears as soon as either budget goes above 1 — equal budgets included. WHY-NOT per-kind hop accounting: it breaks the "expand once, shallowest first" invariant the BFS rests on.
- **`embedDepthOut` governs embedded NOTES only.** Attachment-ness is decided by node-bearing-ness, never by kind (owner decision D5), so `![[chart.png]]` is an attachment exactly like `[[chart.png]]` — the `isNodeBearing` gate drops it before any budget is spent.
- Every root traverses with a **global per-ROLE depth triple** (`DepthSettingsFacts` projects `DepthSettings` into a `ChannelDepths` per root): MAIN uses the active-note trio, every pinned central the pinned trio (ticket `nid_ts4rx2pfo6o18verzk07z16g8_e`). A pinned note that is ALSO the active note traverses as MAIN — the assembler drops the duplicate pin and MAIN-first dedupe backstops it. Within a role, raising a budget extends every root of that role alike. (Per-NOTE depth was designed and shipped, then removed — see **Pinning and settings**.) The BFS is still per-root, so a pinned node keeps its own reach even when disconnected from MAIN.
- Every node is tagged with depth per root per channel; **minDepth** = minimum across all roots and channels is the FIRST level of the truncation priority chain. (It no longer feeds sizing: content-fit sizing dropped the depth-decay metric — see **Sizing** below.)
- **Non-markdown files are never graph nodes.** They are collected as node content (attachments) during traversal.
- **Global node exclusion**: a list of regex-lite patterns (global, like every other setting) matched against each candidate's vault-relative path prunes matching neighbors **at BFS discovery** (before metadata reads / edge recording / expansion). Central and pinned roots are exempt even when they match; a node reachable only through an excluded node is not discovered. The count of distinct excluded paths is surfaced in the view.
- Rebuild triggers: active file change, plus vault file changes while the view is open (debounced metadata resolve, ~500ms).

### Link kinds

Every **outgoing** reference carries a `LinkKind` — `link` or `embed` — which is what splits the outgoing side into two traversal channels with their own depth budgets (ticket `nid_fay1hu5sxcoygizopkkg0f0d7_e`). Vault-generic by design: it says nothing about markdown, canvas or Obsidian.

- **`LinkProvider.getOutgoingReferences`** is the outgoing truth: references in reference order, deduplicated per **(target, kind)** — a note that both embeds and plainly links the same target reports BOTH. `getOutgoingLinks` is the kind-blind view of that same answer (distinct targets), never a second computation.
- **Where the kind comes from.** Markdown body: ARRAY PROVENANCE — `cache.embeds` means embed, `cache.links` means plain link (`EmbedCache` and `LinkCache` are structurally identical, so provenance is the only free signal). `Reference.original[0] === "!"` would be an independent cross-check, but **nothing asserts it** — the suite that did was deleted as circular (it re-derived the kind from a fake), so array provenance is an UNGUARDED assumption pending a real-Obsidian measurement (ticket `nid_t0x7ap99djfuzvz5p261ao7rn_e`). Markdown frontmatter: always a plain link (property links are never embeds). Canvas file node: always an **embed** — it renders the file inline. Canvas text node: whichever the author wrote, since the shared matchers capture the `!`.
- **One degraded path, deliberately:** markdown that `getFileCache` has not indexed yet falls back to `resolvedLinks` keys, which merge kinds, so those references report `link`. Transient and markdown-only — canvases are always parsed precisely so their kinds never degrade.
- **INCOMING stays kind-blind** (owner scope cut). A note you embed is an outgoing embed; a note that embeds you arrives as a plain incoming neighbour. Adding an incoming-embed channel later is additive.
- **Multiplicity stays kind-blind too:** `getLinkCount` counts links and embeds together, because for markdown the number IS Obsidian's own merged `resolvedLinks` count. Splitting it would mean re-deriving the total from the file cache, which could change a rendered badge.
- **Attachment-ness is decided by node-bearing-ness, NOT by kind** (owner decision D5): a diagram is an attachment whether written `[[diagram.png]]` or `![[diagram.png]]`.
- **Frontmatter-id links are a fourth edge source, purely in the adapter** (plan `nid_sjojyvd55emyry45qynphei7o_e`, tickets `nid_dthnhlzp0wzxqhcozj3f8ih5h_e` + `nid_phu0llxhfptse000j66ezrhh3_e`). A configured set of frontmatter field names (`idRefFields` setting, comma-separated, default EMPTY = off) whose values reference another note's frontmatter `id` (which stable-ids writes; we READ only). `ObsidianLinkProvider` merges them into the SAME streams as wikilinks — `getOutgoingReferences` emits resolved id-refs as ordinary `link` edges (deduped against a wikilink to the same target), `getIncomingLinks` returns the referrers of a note's own id, `getLinkCount` adds their occurrences — so they ride the existing channels/budgets with NO new channel and NO engine change. A cache-only reverse index (`FrontmatterIdIndex`: `id → owner path`, `referenced-id → referrer paths`, built from `getFileCache().frontmatter` over `getFiles()`, NEVER a file read) backs the resolution; it warms lazily on the first build and is invalidated by `metadataCache` `changed` + vault delete/rename, mirroring `PerDocStore`. Locked value rules: strings only (scalar or list), unresolved ids skipped, self-references skipped, duplicate id claims won by the lexicographically smallest path. Distinct edge styling is deliberately deferred (a backlog ticket) — an id-ref edge is visually identical to a wikilink.

### Folder-note hierarchy

Folder-note hierarchy is a first-class graph relation: the descendants and ancestors of central notes (MAIN + pinned), each with its own depth budget, a distinct dashed edge, and a flyout explanation (plan `nid_ri1d36t7hmhu0kr652wny1dmz_e`; engine `nid_dit8h888p2ml3092b2zn4zy3u_e`, adapter `nid_bw8hltfj3nsyas03mpfmqn7mg_e`, settings `nid_i3cznjkcnelqzvhp0gqlis499_e`, view `nid_f5bfjoymr2pt7odxieunkxasd_e`, truncation `nid_k4q36qb0nvmusoygl56trgtz2_e`).

- **Folder-note conventions — both, always-on, NO setting.** The 'Folder Notes' plugin convention: `Jon.md` sibling of folder `Jon/`, OR `Jon/Jon.md` inside it, is THE folder note of `Jon/`. When both exist INSIDE wins (`Jon/Jon.md`) and the sibling `Jon.md` is an ordinary note; an extension tie at the same location resolves `.md` before `.canvas`. Only `.md` + `.canvas` participate (`NODE_BEARING_EXTENSIONS`; no `.base`). The folder note is never its own child. The precedence rule is ONE pure module, `src/shared/FolderNotes.ts` (`folderNoteOf` / `childNotesOf` / `parentNoteOf`), shared by the adapter and every test — no duplicated tie-break knowledge.
- **Children** of folder note X = node-bearing files directly in `X/` minus the folder note itself, PLUS each DIRECT subfolder's winning folder note when it is INSIDE-style (it lives one level deeper, so it is not already a direct file — a sibling-style subfolder note already appears as a direct file). One descendant hop = one folder level; a subfolder's OWN files (e.g. `X/sub/y.md` when `sub`'s note is inside-style `X/sub/sub.md`) are reached only at depth 2, and a folder WITHOUT a folder note is not bridged (no synthetic folder nodes). **Ancestors** = one folder-note parent per hop walking up; the first gap stops the walk. Descendants are now SYMMETRIC with ancestors: an inside-style subfolder folder note is descendant-reachable at level 1 exactly as its inside-style ancestor hop already walks up.
- **Two KIND-PURE channels**, `descendants` + `ancestors`, in the ONE existing per-channel BFS (two new `neighborsOf` cases, not a second engine). Consistent with owner decision D1: each channel spends only its own budget on its own hop kind, NO mid-chain kind switching — `descendants=2` walks folder-hop → folder-hop, never a link hop, and a node reachable only via a mixed chain is silently absent (same silence links/embeds already ship). Both channels emit their edge **parent → child** regardless of which direction the walk took, so the arrowhead always points at the child.
- **Depth: each per-role trio became a QUINTET.** New fields `descendantDepth` + `ancestorDepth` on both roles, defaults **MAIN 1/1, pinned 0/0**; a dial at 0 is the off switch (the feature itself is always-on). Same bounded-leaf family as the existing depth dials. UI: rows "Descendants" / "Ancestors" / "Pinned descendants" / "Pinned ancestors" under the existing Depth group in both presenters, each carrying a DESCRIPTIVE hover explaining the folder-note convention.
- **Edge model — "collapse, don't multiply".** An ordered-pair edge carries a RELATION SET: link occurrences and/or the folder relation. This threads engine → flow → flyout as a per-pair `hierarchy: boolean` (`GraphEdge.hierarchy`, `EdgeNotePair.hierarchy`, `FlowEdge.hierarchy`; a collapsed group edge ORs its contributors).
    - **Pure hierarchy edge** (folder relation, no link): DASHED (`.vicinity-graph-edge--hierarchy`, `stroke-dasharray` via `edgeClassName` when `hierarchy && count === 0`; colour/width stay theme defaults), **no count badge** (`count === 0` → no badge, for free), drawn parent → child.
    - **Merged edge** (folder note ALSO links its child, same ordered pair): ONE edge, solid + count badge — visually identical to a plain link edge (owner pick D1-a); the folder relation is discoverable in the flyout, not glanceable. Tracked as pure-vs-merged via whether a LINK channel walked the pair (`linkPairKeys`), NOT via `getLinkCount`, so the links-out=0/descendants=1 case with a real underlying link still renders PURE.
    - **Opposite directions** (child links parent, parent is child's folder note) render as today's two-arrow pair, unchanged. Hierarchy relations never inflate the count badge and are invisible to `getLinkCount` and the cross-links sweep.
- **Flyout**: clicking an edge that carries the folder relation opens the existing link-context flyout with a short **Folder relation** section (`linkPreviewModel.ts` `FolderRelationModel` → `LinkPreviewContent.tsx`) naming the folder note, the folder and the child (e.g. "`Jon.md` is the folder note of `Jon/`; `child-of-jon.md` is inside that folder."), alongside the usual link occurrences when merged. A PURE hierarchy edge still opens the flyout (there are no link occurrences — the "Link occurrences (0)" empty state above the folder section is the truthful signal that the edge is purely structural). The relation is derived purely from the pair's PATHS (source = folder note, target's own folder = the owned folder), so no async / no `FolderNoteIndex` in the controller.
- **Truncation**: hierarchy-discovered nodes get depth tags like any channel and participate in minDepth-first ranking and the node cap with no special casing. The tie-break level by discovering relation kind — **embeds > links > hierarchy** (a node's rank is its BEST kind across its depth tags) — is documented under **Node cap and truncation** below.
- **Seam**: `LinkProvider` (`src/engine/LinkProvider.ts`) reports FACTS `getChildNotes(path)` / `getParentNote(path)`; the adapter's `FolderNoteIndex` (built from `vault.getFiles()` PATHS only, lazy-warmed, invalidated on vault create/delete/rename — mirrors `FrontmatterIdIndex`) answers them by delegating to the shared `FolderNotes` rule. `FakeLinkProvider` grows the same methods for fixture tests.

### Folder grouping (recursive)

Groups nest to arbitrary depth — a note is aware of its ANCESTOR folders and falls into grouping accordingly (plan `nid_xko67wo2z4awg5gdrm1xx1chz_e`, owner-signed-off item-by-item on 2026-08-14). This REPLACED the earlier FLAT, immediate-parent-only grouping wholesale. The grouping tree is DERIVED (no stored-data impact), computed ONCE by the pure `src/view/folderGrouping.ts` `deriveFolderGroups`, whose result — the group list plus the `nearestRenderedAncestorGroupOf` / `lowestCommonAncestorContainerOf` / `projectOntoContainerChildOf` seams — is consumed INDEPENDENTLY by `elkMapping` (container structure) and `flowMapping` (React Flow `parentId`s + edges), which must never re-derive it or they desync.

- **D1 — Always-on, no toggle.** Recursive grouping is the only mode (KISS; consistent with the deleted `groupByFolder` precedent — a second rendering mode would double the layout/edge/e2e matrix).
- **D2 — Grouping rules.** (1) A folder qualifies as a group iff **≥2 visible notes are its DESCENDANTS** (not just direct children); the vault root never groups. (2) Each note renders inside its **nearest qualifying ancestor** folder's group — a lone note in `SQL/sub/` falls into the `SQL` box. (3) Each qualifying group nests inside ITS nearest qualifying ancestor group. (4) **Redundant-chain collapse**: a qualifying folder whose visible content is exactly one child group and nothing else is skipped (no outer box); the surviving group carries the collapsed chain (`chainPath`, e.g. `A/B/C`).
- **A1 — Group label setting.** A "Grouping" settings section with ONE row: **group label = leaf `Folder name` (DEFAULT)** vs **`Full folder path`** (`groupLabelFullPath`, global boolean default `false`). It is a pure TEXT choice — `flowMapping` sources the label from the group model (`leafName` vs `chainPath`; for a non-collapsed group the two are equal, so the setting only ever lengthens a collapsed chain's label), and the box size is computed from packed children + constant paddings with NO label measurement, so it never permutes the layout. The full folder path is always the `FolderGroupNode` tooltip regardless.
- **D3 — Edge collapsing via LCA.** For edge X→Y find the lowest common ancestor CONTAINER (a group, or the top-level canvas pane). Each endpoint projects to its OUTERMOST group strictly inside that container (or itself if ungrouped there). Same-container edges stay passthrough (member-to-member INSIDE a box is allowed); differing projections collapse onto the boundary boxes with a count badge — an edge NEVER crosses a group boundary line. Applies identically to cross links (same pipeline). Consistent with **Rendering and interaction**'s "collapse, don't multiply".
- **D4 — Truncation badges.** A hidden (node-cap-cut) note's per-folder count attaches to the NEAREST RENDERED ANCESTOR group's `+N` badge — where the note would have rendered (`src/view/truncationBadges.ts`, ticket `nid_3wnxsfexabjnx1uj9js2o1c43_e`); the engine keeps hidden counts keyed by immediate folder, and this ancestor attribution is a pure VIEW concern. The corner orphan overlay remains only for counts with no rendered ancestor box.
- **D5 — Interiors pack in phase 1.** Nested boxes pack like big members (`rectpacking`); edge-aware per-container interior layout is a first-class follow-up (`nid_as3hdgn25pbxttimy643f46v7_e`, `nid_7abfje1vus15rx9hzmpel9jin_e`) ending in owner visual sign-off.

### Node cap and truncation

- Hard cap on visible nodes, **a setting, default 100**.
- **All central nodes are exempt** from the cap. Folder group containers do not count toward it.
- Deterministic truncation priority chain: lower minDepth wins, then graph distance to MAIN when connected, then discovering relation kind (embed-found > link-found > hierarchy-only — a node's rank is its BEST kind across all its depth tags; ticket `nid_k4q36qb0nvmusoygl56trgtz2_e`), then pin recency (most recent wins), then docid as final tiebreaker. (The former "higher size score" level was removed with content-fit sizing — nid_cx5zoz7ptucg9nxalibv0mbjb_e: size no longer encodes relevance, so it no longer ranks survival.)
- Truncation is surfaced in the UI: hidden-node count, ideally per folder group.

### Sizing

- **Content-fit** (owner decision 2026-08-03, ticket `nid_cx5zoz7ptucg9nxalibv0mbjb_e`; see `node-sizing-rethink.md`): a node's default size fits **what it shows** — its title lines, its outline entries (bounded by the outline-depth setting), its attachment chip row, its thumbnail — estimated from the same CSS px constants the stylesheet declares, clamped to the user's `minPx`..`maxPx` dials. The composable metric system this section originally specified (own-file-size, total-linker-size, backlink-count, outlink-count, depth-decay, per-metric toggles + weights) was REMOVED wholesale: size sourced from invisible statistics made an empty pinned note the biggest box on the canvas.
- The estimate lives in the ENGINE (`NodeSizer.contentFitPx`), not the view mapping — `GraphNode.sizePx` stays the one diff-stable number every downstream consumer (`nodeDimensionsPx`, elk, the structural diff) reads. The preference-independence rule is deliberately superseded: size now follows the resolved preview kind (`nodePreviewKind`, engine-owned), so flipping the preview preference may relayout — that is the feature.
- **The dials are clamps, not scores** (all three are node HEIGHTS in px): `minPx` floors, `maxPx` ceilings, and `maxPx >= minPx` is enforced at every write and load (`clampSizingSettings`). `minImageHeightPx` (ticket `nid_zv32b4i33zd8c7z69hx10g4zc_e`) is an EXTRA floor applied only to nodes whose resolved preview is the thumbnail, so a picture is legible on an otherwise sparse note — an INDEPENDENT knob, not a cross-field party (no inversion rule with the pair): `NodeSizer` floors image nodes at `max(minPx, minImageHeightPx)` and `maxPx` still caps the result, so it is a floor, not a bypass. It ships at 180px — matching the default `maxPx`, so a thumbnail fills its taller default box (lowering it toward the ~122px natural reveal floor makes image nodes shorter; below that floor it is a no-op).
- Sizing controls live behind an expandable section, not front and center.
- **Centrals (MAIN + pinned, connected or not) get a modest prominence floor**, never a maxPx bypass: `round(minPx + 0.44 × (maxPx − minPx))` (`CENTRAL_PROMINENCE_FLOOR_SCORE`), so an empty central reads as the anchor without dwarfing content-rich neighbours. The fraction was first raised from 0.35 to 0.44 so an EMPTY central cleared the hover pin chip's full-size rung (`nid_tclb98q9hxhmcuonamvr4ig1f_e`); that rung is now gone (`nid_8i5936g90vrllosssaz7v3xbr_e` — the chip is full size by default). Owner-decided to KEEP 0.44 as the final shipped prominence (`nid_s1474ljrdqneqhqt5zrkpwva2_e`): at 40/180 an empty central reads at 102px, a touch more clearly the anchor than 0.35's 89px.
- `sizePx` drives a node's **height**; its **width** snugly fits the title on one line — floored at the content-fit square and **capped** at `NODE_MAX_LABEL_WIDTH_PX` (~250px). A title longer than the cap stops widening the node and **wraps onto the 4 lines** the title CSS allows (`-webkit-line-clamp: 4`, tightened to 2 when a thumbnail shares the node — see below), rather than ellipsizing. The width is a pure char-count estimate (`estimateNodeLabelWidthPx`, engine constants) — no DOM measuring.
- **Every counted region is floored at the height the CSS reveals it** (`NodeSizer.revealFloorPx`): a node whose resolved preview is the thumbnail OR the outline is floored at `PREVIEW_VISIBLE_MIN_NODE_PX` (122px — they share one slot and one container query), and a node carrying attachments at `ATTACHMENT_ROW_VISIBLE_MIN_NODE_PX` (90px). Without it the content-fit sum lands in a band where the node has GROWN for a region the stylesheet still refuses to paint — a two-heading note was 75px of title plus dead space and no outline. The floor is capped by the user's `maxPx` (an explicit maximum is never overruled) and only ever grows a node. Consequence the owner is deciding on (`nid_1mq3t7706vw2kj2kv7ljqlw6l_e`): at the shipped 40/180 dials every note with even one renderable heading is 122..180px.
	- **The CSS density thresholds below are CONTENT-box heights, not node heights** — a size container query measures the container's content box, which is `sizePx` minus the node's border + padding. So the 104px preview threshold is 122px of node and the 72px attachment threshold is 90px, each composed by the ONE helper `revealMinNodePx(rung, isCentral)`; `nodeDensityThresholds.test.ts` re-derives every half from the stylesheet. Confusing the two is what made an earlier version of this floor a no-op.
	- **The chrome is PER TIER**: an ordinary node's is 18px (1px ring), a central's is 20px (the 2px accent ring), so a central floors at 124/92. Not a rounding detail — content-fit sizing lands a central EXACTLY on the floor routinely (a MAIN note with one to four headings), where those 2px are the whole difference between painting the outline and reserving dead space for it. The old sizer pinned centrals to `maxPx`, which is the only reason the band was safe to ignore before.
	- At exactly that floor the thumbnail slot is shown **whole**, not clipped: the reveal block caps the title at the 2 lines the 104px budget allots (the title is `flex-shrink: 0`, so an unclamped long title would otherwise push the 56px slot out through `overflow: hidden`). Budgeting the title in CSS — rather than inflating the floor to ~150px to survive a 4-line title — keeps image-heavy vicinities from ballooning.
- Sizing CONFIGURATION is global-only in V1 — but a node the user has RESIZED is sized by that override alone. `nodeDimensionsPx` returns the stored `sizePx` box verbatim (Q3: the per-node intent is the most explicit one there is, so it outranks the min/max dials, the label-width cap and the thumbnail floor), bounded only by the hard sanity range `NODE_OVERRIDE_HARD_MIN_PX`..`NODE_OVERRIDE_HARD_MAX_PX` (24..1200), which `clampNodeSizeOverridePx` applies on the store's write AND load paths so the view never has to re-judge it.

### Pinning and settings

- Pinning a node makes it an **extra central node**: its vicinity is traversed and rendered alongside MAIN's. The pinned set is global state and survives restarts.
- **Local pins are a SECOND pin kind, scoped to one MAIN** (owner decision 2026-08-07, tickets `nid_ndoy0bq50w1p1qzd2i9di2fxo_e` / `nid_2zm28ijiqp786yw6grwbvmffv_e`): a **local pin** marks a target note as pinned ONLY while a specific MAIN (active) note is active. Global pinning is unchanged; a note can hold both pin kinds at once. When its main is active, a locally pinned note behaves EXACTLY like a globally pinned central — same pinned depth trio, `isCentral`, cap-exempt, its own vicinity even when UNLINKED from MAIN, and it survives restarts. Local pins are stored as a docid-keyed map `localPins` (MAIN docid → target `PinnedDocEntry` list); both sides are docids, so renames on either end stay non-events. Minting a docid on the un-clicked MAIN is sanctioned (the user acts "in the context of" that main); the same `DocPersistEligibility` refusal governs both docs, naming which one refused. **The ENGINE is unchanged**: the adapter merges global ∪ the active main's local pins into ONE pinned-root list (deduped by docid, keeping the most-recent `pinTimestamp`) before the engine sees it — local-vs-global is a persistence/view fact, not a traversal fact. The VIEW recovers the distinction as two per-node flags (`isGloballyPinned`, `isLocallyPinned`), each with its own toggle. This is the **first sanctioned per-main-doc layer**, superseding the 2026-07-29 global-only rule for PINS ONLY; every other setting stays global.
- **Every other setting is GLOBAL — one value, one layer** (owner decision 2026-07-29, ticket `nid_ez38gf1mrdgh5kxedzrdicwzl_e`). Depth is global per ROLE — one trio for MAIN, one for every pinned central (never per note); view settings (sizing, cap, node contents, force layout) and node exclusion apply to every view. There is no per-document layer and no cascade to resolve, so both settings resolvers were deleted rather than kept as identity functions.
    - **WHY-NOT the per-doc model this plan originally specified** (per-document depth/view overrides, per-viewing-doc `centralDepths`, pin-on-toggle, per-control reset-to-global): it cost ~900 production lines that existed only for it (plus ~1300 more carrying per-doc branches and ~1700 test lines) to remember state nobody had asked to be remembered yet, and it forced every downstream settings surface to carry a per-doc arm. Pre-release that is not paying for itself. It stays reachable: the pins are still docid-keyed, so a future per-doc layer would be additive.
- The UI needs unpin controls on pinned nodes themselves, and pinned centrals are styled distinctly from MAIN. Resetting is **per settings-tab section plus one tab-wide scope** (`view/settingsResetPlan.ts`), not per control — with one global value per field there is nothing for a per-control reset to clear. Every reset keeps the pinned set.
- **Both settings surfaces render ONE declared row model** (`view/settingsRows.ts`, ticket `nid_armoson86j0ii8c33r1odo1rc_e`): the same sections, in the same order, under the same names, with every setting present on both. What differs is presentation only — the panel is ~260px, so it uses compact controls (depth steppers rather than sliders), moves descriptions into hover tooltips, and shows the exclusion **pattern list read-only** (a multi-line regex list needs the settings tab's room). Obsidian's `Setting` API cannot mount in React, so the two RENDERERS stay; the model is what makes their parity structural. A row that depends on another setting (exclusion patterns on the exclusion flag) declares `disabledWhen` and is rendered ALWAYS, disabled — a control that vanishes costs the reader their place, and stored patterns must stay visible before a reset destroys them.
- **Both settings surfaces write through ONE pipeline** (`view/settingsWritePipeline.ts`, one instance per plugin), which fixes what users actually saw (ticket `nid_m5hxe4eo9jgt7cfic7s2o3uvi_e`). The guarantees it states:
    - **Nothing a control shows lags the input.** A stepper, slider, toggle or typed field moves on the interaction; the graph rebuild that carries the value back is allowed to take as long as it takes. Precisely: the control keeps showing what the user last asked for while the store still holds the value the burst STARTED from, or one of the burst's own earlier values (its writes echo back one at a time — flickering through them would be worse than lagging). The store wins the moment it holds what the latest request will actually STORE, or anything else — another surface wrote — so a control can never claim a value that was not stored. A control whose field is clamped on the way in (the sizing numbers) tells the rule what the clamp will store, so that "typed past a bound the field was already sitting on" — where the store never moves at all — hands authority back too, instead of showing an unstored number until the next edit.
    - **Two edits made in one breath both survive.** Every edit names ONE field and the pipeline merges it over the globals as they are AT WRITE TIME — never over the snapshot a control rendered from, which is what used to make a second edit silently revert the first.
    - **Click order is store order.** All writes (settings AND pins) share one serial chain, so the value the user acted on last is the value that lands.
    - **A restore-defaults never redraws ahead of itself.** It flushes pending typed edits, writes the defaults, waits for the chain to go idle — including a control used WHILE it ran — and only then rebuilds the tab. The waiting happens even when the defaults write FAILED: a failure is exactly when the tab must show the truth, and skipping the drain there would reinstate the bug.

### Persistence

- All storage is **JSON**.
- **Storage is TWO-TIER** (owner decision 2026-08-10, ticket `nid_8f8ey41extajt08zphwwxhnwq_e`):
    - **`data.json` via `saveData`/`loadData`** holds the truly-global CONFIG: the global settings dials (`globalDepths`, `globalView`, `nodeExclusion`) AND the global pinned SET (`pins`, a docid-keyed map). A pin is config — Obsidian manages what is globally pinned — not vault content, so it stays here.
    - **The per-file `VaultFileStore`** (`${VAULT}/.plugin_data/vicinity_graph/per_file/<docid>.json`, one file per doc) holds the per-doc / per-main FACTS, syncing as vault content alongside the notes they describe: each doc's SUBJECT override (`nodeOverrides`: optional `sizePx` box, optional `content` choice; see `docs-internal/plan/node-sizing-rethink.md`) and its MAIN-context `localPins` (MAIN docid → target `PinnedDocEntry` list). `PerDocStore` owns these — the in-memory-authoritative, warm-once mirror of that directory, the per-file analogue of `PluginDataStore`. A record with every section empty is deleted, not written empty. `localControls` is reserved (empty) for a future per-main dials layer (ticket `nid_rnghlzs0uejjlbd5a4bjkq7eg_e`), which is a change to that record shape ALONE.
    - No SETTING is written per document; `localPins` is a per-main-doc PIN layer (owner decision 2026-08-07), not a settings layer, and like every map here it is a global fact keyed by docid. Both keying halves — MAIN and target — are docids, so renames on either end stay non-events.
    - This DISCHARGES the parked sync-friendliness note: the per-doc facts now live in a per-file, vault-synced store (the argument the original per-doc plan made), while config that is NOT vault content stays in `data.json`. The store PRIMITIVE (`VaultFileStore`) is domain-agnostic and reused. The original location (`.obsidian/plugins/<id>/doc-data/`) was NOT resurrected — `.plugin_data/vicinity_graph/` is the store's own root. Any pre-existing `doc-data/` directories remain dead files (clean break while unpublished, `CLAUDE.md`).
- **docid is a stable unique id** from the submodule library. Markdown docs: frontmatter. Canvas docs: Obsidian's native canvas `metadata.frontmatter`, which survives canvas edits. Stable ids make renames a non-event.
- Deletes: `vault.on('delete')` plus an in-memory path-to-docid map for live cleanup, and an **orphan sweep** for everything else. Both drop the doc from **every** docid-keyed collection at once — the pinned set (`PluginDataStore.forgetDocs`) AND the per-file store's node overrides + localPins, where a deleted doc can be a MAIN key AND a target under other mains, so both positions are pruned (`PerDocStore.forgetDocs`; its reverse index makes the target-side prune cheap). The two `forgetDocs` calls are the ONE conceptual choke point spanning both storage tiers, invoked side by side by the live handler (for docs the map knows) and the sweep (for any entry whose doc no longer resolves). The read-side twin `PerDocStore.keyedDocids` reports both local-pin positions (and every override docid), so the builder unions it with the pinned set's docids and the on-demand warm-up resolves them all on the first build after a restart.
- Sweep constraints: **delayed start (~15s after plugin load)** so it never competes with startup, and **chunked with yields** (process a batch, `await sleep(0)`, continue) since async alone does not protect the single-threaded main loop.
- Every persisted shape carries a `version` field from day one.

### Canvas support

- Canvases are first-class docs: they can be nodes, centrals, and pinned.
- **We own canvas parsing — for every canvas, unconditionally** (ticket `nid_fay1hu5sxcoygizopkkg0f0d7_e`, option 3a). `resolvedLinks` is never consulted for canvas links. Two reasons, both fatal to the older adaptive strategy: (1) `resolvedLinks` is a merged link+embed COUNT, so a core-served canvas could not say which of its references are embeds — and embed-ness is now a first-class fact (see **Link kinds**); (2) whether core has indexed a given canvas is a boot race, so consulting it made the reported facts depend on launch timing. The cost is one `vault.read` + `JSON.parse` per canvas, already mtime-cached by `CanvasParseCache`, resolved through the same `getFirstLinkpathDest` core itself uses. **Superseded:** the former per-canvas `core-indexed` / `fallback-required` split (`CanvasCapabilityDetector`, now deleted).
- **Settled canvas edge semantics (tickets `nid_s676x55uojmtcwh9t4l9mc6zl_e`, `nid_ygo7h95ssgmunaqsprc1zlmfh_e`), binding on BOTH paths:** a canvas links whatever its FILE nodes reference AND whatever the links inside its TEXT nodes reference — a text node is markdown, so that means wikilinks (`[[note]]`, `![[note]]`) AND markdown-style inline links (`[a](note.md)`, `![alt](pic.png)`) alike. Every text-node link resolves exactly like a markdown body link (`getFirstLinkpathDest`, relative to the canvas), so aliases and `#subpaths` resolve to the document and dangling links produce no edge; a markdown-style destination reaches that same resolver normalised to link text (title dropped, `#`/`?` stripped, then percent-decoded — in that order, so an encoded `:` cannot masquerade as a URI scheme). Destinations carrying a URI scheme or protocol-relative `//host/…`, external `link` nodes and `group` nodes reference no document. A destination with an UNENCODED space is not a link at all (CommonMark forbids one in a bare destination), so it yields no edge — truncating it at the space would name a different, possibly existing document, and a WRONG edge is worse than a missing one.
- **What core itself indexes is MEASURED, not assumed** (it is no longer a link SOURCE for us, but our parse must still report the same edge set users see elsewhere in Obsidian) — `e2e/canvasMarkdownLinkIndexing.e2e.ts` reads `resolvedLinks` out of a real Obsidian (1.12.7) for a canvas text node carrying every destination shape. Observed: markdown-style links ARE indexed, keyed by resolved path (`{"md-links/target.md": 4, "md-links/spaced target.md": 1}`); `%20` resolves to the spaced file; an unencoded space and an external URL produce nothing; and `getFirstLinkpathDest` — the seam the fallback resolves through — accepts `target.md`, `./target.md` and `../md-links/target.md` alike, so relative destinations resolve identically to core's. Every unit-level parity test hand-seeds `resolvedLinks`, so that spec is the only thing that can falsify the premise our parser is built on.
- **Why our parse must match core's edge set:** the same canvas is visible in Obsidian's own graph and backlinks panes, so a divergence reads as a bug in us. (Historically this mattered even more: the two sources both SERVED edges, and which one a rebuild landed in was a boot race — "the graph depends on how fast you opened it". Always-parsing removed the race; the agreement requirement outlives it.) Code regions agree too: core indexes no link written inside a code span or fenced block (measured in `e2e/canvasMarkdownLinkIndexing.e2e.ts`), so our parser masks those regions (`src/shared/MarkdownCodeRegions.ts`) before matching. Residual, deliberately unhandled there: indented (4-space) code blocks, escaped brackets, and a code span that crosses a newline. Edge ORDER is not contractual on either path — the fallback scans a text node once per syntax, so it reports wikilinks before markdown-style links rather than in written order.
- The text-node scan rides the mtime-keyed `CanvasParseCache`, so it costs nothing per rebuild; only link RESOLUTION re-runs, because a rename changes a target without touching the canvas's mtime.
- **Our parse is the SOLE authority per canvas edge — set AND count.** Consequence of always-parsing, and a declared behavior change from the adaptive era: for a core-indexed canvas the edge-count badge used to be core's `resolvedLinks` number and is now our occurrence count (pinned in `ObsidianLinkProvider.test.ts` with a canvas whose two numbers differ). Sourcing the count from core while the edge set comes from us would split one edge across two authorities and put the badge back on the indexing boot race.
- Whether an OLDER install indexes canvases is unknown and no longer matters: core's index is not consulted for canvas links on any install, so there is no install-dependent behavior left to detect.

### Rendering and interaction

- Custom node component: title, **first image as thumbnail** (lazy-loaded, fixed height, "+N" badge for more), **icon strip per attachment extension with counts**, click on an icon opens a dropdown listing those files. Everything past the first image loads lazily; rely on React Flow viewport culling.
- **In-node markdown outline** shares the thumbnail's preview slot: a node above the 104px container-query threshold shows EITHER its heading outline OR its first image, decided by the global three-way **Preview** setting (`auto` | `outline` | `image`, default `auto`, exposed as a pill on the settings tab AND in the graph controls panel). Under `auto` — the shipped default — the outline is a **root's** affordance (owner decision 2026-08-05, ticket `nid_k2pa8khm6ugozmhkd6nlbdrq6_e`): for a CENTRAL (`TraversedNode.isCentral` — MAIN and every pinned root) **document position decides**, exactly as it always has — an image before the first heading wins, the documented "show the picture" escape hatch. For an ordinary neighbour the `auto` ladder is **first image anywhere → title only**, never the outline. WHY: with content-fit sizing any note with ONE renderable heading floors at the preview reveal rung, so an outline offered vault-wide turned the graph into a wall of near-identical big boxes; cutting the DEMAND for the preview slot (rather than lowering the CSS rungs) leaves a big box meaning "there is a picture here" / "this is a root". `outline` / `image` are opt-in overrides of BOTH that position rule and the tier rule, and neither can empty a node (a preference with nothing to show falls back to the other kind). Until per-node content overrides ship (`nid_9hx6okamx3yt0rg9iad2f4151_e`) the only ways back to a peripheral note's outline are pinning it or the global `outline` preference — an accepted interim gap. Rendered as a real nested list, capped by the global **Outline depth** setting (1–6, default 2) plus a render budget, scrollable with a hover-only scrollbar and per-entry ellipsis. Owned by a dedicated `NodeOutline` component so the UI can be iterated independently of node rendering.
- **Where that decision lives:** the adapter (`ObsidianLinkProvider`) only reports the FACT (`FileMetadata.imagePrecedesOutline`) and always extracts the outline; the precedence rule is one pure function, `engine/nodePreviewKind.ts`, applied over the depth-filtered outline plus the traversal's tier fact (`isCentral`). The chosen kind travels as `FlowNodeData.preview`, so `NoteNode` renders and decides nothing. The rule moved to the ENGINE with content-fit sizing: the sizer must reserve space for the same region the view paints, so `sizePx` now DOES depend on the preference (a flip may relayout — see Sizing), and the reveal floor keys off the chosen preview kind rather than off "the note has an image". The 104px/72px thresholds are knowledge held in both the stylesheet (as content-box heights) and `PREVIEW_VISIBLE_MIN_NODE_PX` / `ATTACHMENT_ROW_VISIBLE_MIN_NODE_PX` (as those plus the node's own chrome — 18px, 20px for a central's ring; see Sizing); `src/view/nodeDensityThresholds.test.ts` parses the CSS and fails on drift.
- Folder groups render **only at 2+ members** (a folder qualifies on 2+ **descendants**, not just direct children — see **Folder grouping (recursive)**) and NEST inside one another; a folder with a single visible note is not a box — that note falls into its nearest qualifying ancestor group instead. Group colors: deterministic hash of folder path into a palette (user-assignable later).
- **Edges show direction** (arrowheads). A→B and B→A render as **two arrows**, offset with opposite curvature. Multiple links between the same ordered pair collapse into one edge with a count badge.
- **WHICH links become edges is a setting — "Show cross links", global, default OFF** (ticket `nid_puf4a4q6fgn5lpehh5dowfm1r_e`; supersedes the fixed walked-only rule of step-02 CLARIFICATION Q5). OFF: only the links the BFS actually walked, the original "cleaner graph". ON: the walked set UNIONED with the INDUCED SUBGRAPH over the visible nodes — every link whose source and target are both on screen, including a link between two frontier notes the walk never took. The union is by construction (the walked edges seed the sweep's accumulator), so ON is a guaranteed SUPERSET of OFF even though the sweep reads `getOutgoingLinks` while the incoming walk reads `getIncomingLinks` — in Obsidian those are two independent authorities and the file cache degrades during the boot window, so a derived-from-outgoing-only union could otherwise DROP a visible edge. The sweep runs POST-truncation, so **node selection is unaffected**: sizing and the truncator's distance-to-MAIN ranking keep running on the walked edge set, and the visible node set is identical either way. Cross links are rendered, counted (`getLinkCount`, same `Math.max(1, …)` floor) and collapsed exactly like walked ones — deliberately NO provenance flag and no styling seam.
- Styling pulls from **Obsidian theme CSS variables**, so light/dark themes just work.
- Interactions: click opens the note, **clicking an outline entry opens it at that heading** (same ctrl/cmd new-tab gesture), ctrl/cmd-click for the alternate target. **No hover preview**: nodes do NOT fire Obsidian's `hover-link` (removed, ticket `nid_jnw75pg24q4itujs8vfgqj4mh_e`) — the node already shows its own outline/thumbnail, so a popover on hover only covered the graph the human is reading.
- **The hover pin chip is on EVERY node, at every height** (ticket `nid_tclb98q9hxhmcuonamvr4ig1f_e`, owner-decided): it used to be gated on the 72px density rung, which content-fit sizing turned into the common case — a title-only note sits at minPx and had no pin affordance but the right-click menu. **And it is the SAME SIZE throughout** (ticket `nid_8i5936g90vrllosssaz7v3xbr_e`): the chip used to GROW at that same 72px rung, i.e. on HEIGHT alone, so the common small node — short but as WIDE as its title — wore the tiny chip with its corner half empty. Full size (20px, `--size-4-1` inset) is now the DEFAULT, and `graph-view.css` only ever steps it DOWN, on rungs that are arithmetic rather than judgement calls: a corner chip reaches `inset + size` into the node's padding box, so it covers the node's centre point — where a click means "open the note" — only when BOTH content-box axes are within `2 × reach − 16px` of padding. At ≤32px on both axes the chip goes COMPACT (14px, 3px inset, via custom properties the rung re-declares); at ≤18px on both axes even the compact chip sits on that centre point, so there it is withheld and pin/unpin stays on the right-click menu. `minPx` is a dial the user can take to 1px and a drag-resize override may be 24px, so those bands are reachable — but a node small on ONE axis never enters them, which is the whole point. The `pointer-events: none`-while-hidden guard is unchanged. Both rungs are guarded in `nodeDensityThresholds.test.ts`, each re-derived from the declarations of the chip it steps DOWN from, plus a monotonicity guard so no rung can grow the chip again and a descent guard so no rung's band can swallow the band above it (each rung derives from the chip above, so a step-down that traded size for inset would consistently derive an inverted ladder). A THIRD guard holds the corner the chip shares with the drag-resize right-edge grip: that band reaches 4px into the node and hit-tests above it, so each rung's `border + inset` must clear it (this is why the compact inset is 3px, not 2px). The rendered halves — a short-but-wide node's chip matching a large node's, the square minPx node stepping down, the chip withheld at the drag-resize floor, and the node still opening on a body click at every size — are e2e in `nodeResize.e2e.ts`, driven through a stored size override.
- **Drag-to-resize** (ticket `nid_qjsj5mth2phdqctbm0vfx9elw_e`): hover-revealed React Flow `NodeResizeControl`s on a note's RIGHT edge, BOTTOM edge and bottom-right corner — deliberately no top/left grips, which resize by moving the node's ORIGIN, and positions are layout-owned, so the move would snap back on the next rebuild. The drag is local to React Flow (which is why the flow component keeps its nodes in local state and applies `onNodesChange`); **release** commits the box as the doc's `sizePx` override through the same guarded `data.json` seam a pin uses, and the pipeline's fan-out is the ONE rebuild. The node's right-click menu offers **Reset size** only while an override exists. A refused write (no stable id) still repaints — the released box is already on screen, and nothing stored it (see `GuardedWriteOutcome`).
- View placement: **right sidebar by default** (matches native local graph muscle memory), registered as a normal view type so it can be dragged into the main area. Follows the active file; per-leaf `getState`/`setState` so workspace restore works with multiple views open.

### Layout stability

- After each rebuild, **diff the node/edge structure**. Unchanged structure skips layout entirely and only refreshes node data.
- Exception: if any surviving node's RENDERED box (`nodeDimensionsPx`, in either dimension — so an engine size and a wider title both count) grew beyond **`SIZE_RELAYOUT_THRESHOLD`** (a named constant, initially 1.0, meaning +100%, e.g. a large paste), trigger a full relayout so the graph does not turn ugly.
- Exception: a surviving node whose per-node size **override** CHANGED — set, cleared or moved to another box — is judged by ONE question of its own, threshold or not (tickets `nid_sj9qg27cmear9lgdlz5umwra5_e`, `nid_9ep12hkmk4zjv2p28emmrhieq_e`): **does the new box still FIT where the rendered layout put it?** (`view/layoutFit.ts`, over the positions and folder-group boxes the reuse path would keep). It fits ⇒ reuse the layout: the user made ONE node bigger and the graph around it was fine, so re-arranging it — and re-fitting the viewport with it — is a jump nobody asked for. It collides with a neighbour, spills outside its own folder-group border, or grows into another group's box ⇒ relayout, because reusing those positions is exactly what left the node overlapping its neighbours. Geometry the rule cannot see (no rendered layout yet, a node with no cached position) answers "no fit", i.e. relayout — conservative by construction. The growth THRESHOLD does not apply to a resized node at all: it damps PASSIVE growth, where a jump under the reading position is the bigger evil, and re-judging a resize by ratio would relayout a big-but-fitting box through the back door. The anchor is the node's existing top-left — only right/bottom/corner grips exist, so a resize never moves the origin. It cannot fire mid-drag: the drag lives in React Flow's local node state and reaches the store only on release. Consequence, accepted: a relayout bumps `layoutVersion`, so a NON-fitting release also refits the viewport — ticket `nid_ct22qotgtw4rezbdn5m0diyb3_e`. WHY-NOT a required clearance between boxes: plain overlap is the honest question, and a second spacing number here would be a second opinion on the layout's own knobs.
- Structural changes accept layout jumps in V1. Position-seeding elk for incremental stability is a V2 refinement.

### Testing

- **The engine is pure**: traversal, sizing, truncation, and settings resolution are functions with no Obsidian imports, tested against a fixture-driven **FakeLinkProvider**. The `LinkProvider` interface is the only boundary to Obsidian and the seam where canvas knowledge — and link-vs-embed knowledge — lives.
- Fixture suite includes canvas JSON files for the canvas parser. Canvas coverage is written as PARITY tests: the same canvas is asserted with and without core's `resolvedLinks` entry present, which must make NO difference to the answer, and the answer must be the edge set core reports (see the settled semantics under **Canvas support**). Those tests hand-seed the core side, so what core ACTUALLY indexes is pinned separately by `e2e/canvasMarkdownLinkIndexing.e2e.ts` against a real Obsidian.
- Obsidian adapter code stays thin; correctness lives in the tested core.

## Phased Plan

**Phase 0, scaffold.** Plugin template (TS, esbuild), React 18 in an ItemView, vitest, submodule wired, manifest with minAppVersion. Deliverable: empty plugin loads in a dev vault, tests run.

**Phase 1, core engine.** Pure and fully tested: types, LinkProvider interface + fake, multi-root directional BFS with attachment collection and min-depth tagging, truncation with the priority chain, sizing engine, settings resolution. (The resolvers shipped here carried the per-root/per-view cascade; with settings global-only they became identity functions and were deleted.)

**Phase 2, Obsidian adapters.** ObsidianLinkProvider over resolvedLinks/getBacklinksForFile, canvas capability detection, fallback canvas parser against fixtures. Includes the devtools verification of what the install actually indexes.

**Phase 3, persistence.** data.json globals and pins; id resolution via the submodule; delete handling; delayed chunked orphan sweep. (Shipped with a per-doc `doc-data/` store too; that half was later removed — see **Persistence** and `docs-internal/plan/steps/step-03-adapters-and-persistence.md`.)

**Phase 4, view shell.** ItemView + React, MAIN tracking and follow-active-file, per-leaf state, rebuild pipeline: events → engine → structural diff → elkjs → React Flow. Deliverable: first visible graph with plain nodes. The milestone where it feels real.

**Phase 5, rendering.** Rich nodes (thumbnails, icon strips, dropdowns), MAIN/pinned/regular styling, folder groups, directed edges, truncation badges, theme integration.

**Phase 6, controls.** In-view toolbar: one pair of global depth steppers, expandable sizing controls, cap setting, pin/unpin on nodes. Global settings tab for every setting, with per-section restore-defaults rows. (Shipped as a central selector with per-central steppers and per-control reset-to-global; replaced when settings became global-only — see `docs-internal/plan/steps/step-06-controls.md`.)

**Phase 7, hardening.** Dense-vault fixtures, cap edge cases, image-loading and rebuild-frequency performance pass, README.

Rationale for the order: Phases 1 through 3 contain every design decision in this document and run entirely without Obsidian, so rework risk concentrates where iteration is cheapest. The UI consumes a stable, tested engine.
